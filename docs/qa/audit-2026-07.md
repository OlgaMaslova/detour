# Detour live-product audit — July 2026

**Audited:** 2026-07-15  
**Frontend:** https://detour-app.supernaut.to  
**API:** https://sn-pb-repo-1297566350-6aebd3.fly.dev  
**Scope:** Public discovery across Madrid, Paris, and San Francisco; venue details and source attribution; invite-only community; responsive layout; and live PocketBase collection access rules.

## Executive summary

No critical finding was identified. The Madrid and San Francisco map experiences are polished and usable on desktop and a 390px mobile viewport. Venue cards and details consistently use source-specific recognition language and link to named official guides. Protected community records were not exposed to unauthenticated requests, and server-side hooks—not only the UI—enforce invite redemption, member-owned evidence, and verified-member submission.

Two high-severity product blockers remain:

1. The live community has no issued invitations, leaving no path for a real person to join or to become an invitation issuer.
2. Paris is selectable as a map-first experience even though every one of its 29 venues has a `0/0` location sentinel, yielding a full-height but pinless map.

## Test method and evidence

### Browser flows

- Loaded the live frontend at desktop width and at **390 × 844** mobile width.
- Switched among Madrid, Paris, and San Francisco.
- Opened venue details from the list and checked source attribution links.
- Opened the member panel and attempted an invitation signup with a deliberately invalid `.invalid` address and code. The server correctly rejected it with: “This invitation code is invalid or has already been used.” No account was created.
- Inspected the Madrid and San Francisco map surfaces, pins, selection details, filters/search controls, and the Paris empty-map state.

### Live data and API rules

Read-only live inspection found:

- **82** `venues`: Madrid 43, Paris 29, San Francisco 10.
- **92** `venue_awards` and four named guide sources.
- **1** `members` record, the reserved non-interactive curation-proof account.
- **0** `invites` records.
- **3** approved `visit_evidence` records for the proof member and **1** pending `detour_submissions` proof record.
- Unauthenticated direct list requests to `members`, `invites`, `visit_evidence`, and `detour_submissions` returned empty lists, not private records.
- Public catalogue reads for `venues`, `venue_awards`, and `guide_sources` are intentional and required by the map client.

The deployed community migration and hooks were also inspected against the live schema. They set owner/status fields on the server, require a valid unused invite during member creation, restrict private reads to the owning member, and require verified membership both in the collection rule and in the create hook before a recommendation can enter the curation queue.

## Findings

### High — H1: Community enrollment has no bootstrap path

**Affected flow:** Member join and downstream verification/submission flow.

**Evidence:** The live `invites` collection has **0** records. The only member is the reserved curation-proof account, whose credentials are intentionally unavailable. The member UI directs visitors to use a personal invitation, and the live invalid-code attempt was correctly refused. Since only an authenticated member can create an invitation, no real visitor can become the first member or issue the first valid invitation.

**Impact:** The invite-only community cannot onboard a real person. Consequently, real visit verification and verified-member recommendations cannot be exercised in production.

**Recommended fix:** Establish an operator-only bootstrap procedure before launch: create or designate an initial real member, issue one or more server-generated invitations for controlled distribution, and document how curators replenish invitations. Keep invite issuance server-side and preserve the existing one-time redemption constraint.

**Reproduction:**

1. Open **Members** on the live frontend.
2. Select **Use an invitation** and submit valid-looking registration details with any unissued `DTR-…` code.
3. Observe the rejection message.
4. Confirm with a privileged read-only count that `invites` has zero records.

**Resolution status — backend resolved; frontend release pending (2026-07-15):** `1767980000_harden_catalogue_and_bootstrap_invites.js` is live and created three random, one-time bootstrap invitations under the reserved non-interactive issuer without committing any code. The committed signed-in member panel lists only the member’s own unclaimed invitations and can issue another server-generated personal invitation; its production release is blocked by an existing Cloudflare deployment-slug conflict.

### High — H2: Paris breaks the map-first promise

**Affected flow:** Paris city discovery and venue detail selection.

**Evidence:** All **29** live Paris venue records have `lat: 0` and `lng: 0`. The frontend correctly treats `0/0` as an unknown-location sentinel, but still renders a large Leaflet map with no venue pins. The UI then says “Map positions for this selection are being refined. Every place is still listed below.” Paris also remains presented as a selectable city in a map-first product.

**Impact:** A guest who switches to Paris gets no map discovery, cannot select a Paris venue from a pin, and sees copy/meta copy that implies a mapped collection. This is a core-product failure rather than a minor data gap.

**Recommended fix:** Add verified Paris addresses and coordinates before presenting Paris as map-first. Until then, either remove Paris from the map selector or render it as an explicitly list-first preview with no map or nearby-location control. Update the Paris meta description at the same time; it currently says the selection is “gathered on one map.”

**Reproduction:**

1. Select **Paris, France** in the city picker.
2. Observe the 29 listed venues and the empty map surface.
3. Inspect the live `venues` records filtered by `city = 'Paris'`; each record uses the `0/0` sentinel.

**Resolution status — implemented; production release pending (2026-07-15):** Paris remains available as an explicitly labeled list-first preview in the committed frontend. It removes the vacant map and nearby-location control, uses accurate title/meta/editorial copy, and preserves list-card detail browsing. Madrid and San Francisco retain their map-first presentation. The production release is blocked by an existing Cloudflare deployment-slug conflict.

### Medium — M1: Public catalogue endpoints expose internal coordinate-research notes

**Affected collections:** `venues.coord_verification_note`; `venue_awards.verification_note`.

**Evidence:** Both fields are returned by unauthenticated public catalogue API responses. Sample values disclose internal research detail such as OpenStreetMap object IDs, building-centroid judgments, duplicate-name resolution, and “needs_review” language. The UI deliberately does not render those notes, but a direct public request exposes them.

**Impact:** No member personal data or curation-queue data is exposed. However, internal editorial/research notes can undermine confidence in a premium map product and make incomplete location work unnecessarily visible.

**Recommended fix:** Replace client reliance on free-form research notes with a public boolean/status such as `approx_location`, then mark the detailed research-note fields hidden or serve a field-limited public read model. Retain detailed provenance for operator use only.

**Reproduction:**

1. Request the public `venues` or `venue_awards` list endpoint without authentication.
2. Inspect `coord_verification_note` or `verification_note` in the returned records.

**Resolution status — resolved (2026-07-15):** the same hardening migration hides both detailed research-note fields from public records and adds the narrow public `approx_location` flag used by the map client. Internal provenance remains stored for editorial use.

---

### Low — L1: Paris copy and metadata conflict with the current product state

**Affected copy:** Paris hero/footer and page metadata.

**Evidence:** The live page openly says positions are being refined, which is candid. However, the page is still introduced through a map-first city switcher and the Paris description says the venues are “gathered on one map,” although no place is mapped.

**Impact:** The mismatch makes an otherwise honest editorial tone feel less precise.

**Recommended fix:** Ship the H2 product decision with copy that accurately labels Paris as a list-first preview until mapping is complete, or restore map-ready language only after verified coordinates are available.

## Confirmed controls and strengths

### Discovery, details, and copy

- Madrid has 43 venues; 41 render as map pins. The two unpinned records are called out without publishing coordinate-style language.
- San Francisco has 10 venues with working pins and a correctly framed map.
- Venue details show source-specific labels—such as Michelin Stars, Guía Repsol Soles, and ranked-list positions—without conflating ranking numbers with star/sole counts.
- Every inspected card/detail provides named official-guide attribution. External links use safe new-window attributes.
- The mobile layout at 390px preserves readable controls, a usable map, cards, and source links with no visible horizontal overflow.

### Community and API-rule security

- `members`, `invites`, `visit_evidence`, and `detour_submissions` did not reveal records to an unauthenticated visitor.
- Member profile list/view rules are self-scoped. Visit evidence and curation submissions are likewise member-scoped, so one member cannot list another member’s notes or recommendations.
- Invite creation assigns the issuer and random code server-side. Member creation rejects missing, invalid, and already-claimed codes server-side.
- Visit evidence is server-attributed and forced to `pending`; authenticated clients cannot supply another member ID or self-approve a visit.
- Recommendation creation checks `community_status = 'verified'` in both the collection rule and the server hook, then forces the recommendation into the private `pending` queue.
- The live proof data demonstrates three approved visits and a pending queue entry, while the public API did not disclose that queue entry.

## Non-blocking audit limitations

The reserved verified proof account intentionally has no interactive credentials. I therefore verified the verified-member recommendation path through the live protected data, deployed rule/hook logic, and unauthenticated-access checks rather than submitting a new live recommendation. Once H1 is resolved and a real controlled test member exists, repeat a create-and-cleanup smoke test for the complete invite → three approvals → recommendation path.

## Resolution priority

1. Fix **H1** before positioning the community as live.
2. Fix **H2** before positioning Paris as a map-first city.
3. Address **M1** in the same backend hardening pass, then re-run public API inspection.
